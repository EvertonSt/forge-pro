Forge Pro — Desktop App

The vendor portal as a native Windows application. Submit templates and components, watch the automated QA gate pass or reject them, fix and resubmit, and take a listing from deployment to sale — all in demo mode, with no server, database, or internet required.

Two roles, one window
The app has two built-in demo identities. As a vendor you create and manage submissions. As an admin you approve vendors and govern what goes live. You switch simply by visiting the right area — the dashboard is the vendor home, and the admin area is linked from it. No login screens; both are ready to use.

1 · What this app is (and what it is not)

Forge Pro is an AI-native marketplace for website templates and UI components. Its defining feature is the automated QA gate: every vendor submission is tested by a real browser before it can go live — responsive checks, a broken-link crawl, visual regression, and Lighthouse performance/accessibility scores.

This desktop app wraps the vendor portal in a native Windows window. It runs the portal's real production build in demo mode: the data lives in a small file on your computer instead of a database, and the QA runner is simulated with one click. Everything you do works exactly the way it will in the live marketplace — that is the point of the demo.

What's real

  • The full submission workflow: catalog details → preview-ownership proof → artifact upload → QA → publish/withdraw.
  • Real validation: URL rules, zip format and size checks, SHA-256 hashing, semver, price bounds.
  • Real QA report rendering: the same report contract the live runner produces, with score bars and failed checks.
  • Real admin governance: approve/revoke vendor applications, unpublish live items.

What's simulated (demo only)

  • Data: a file-backed demo store (persisted in your user folder) instead of Supabase.
  • The QA run: the "Simulate pass / Simulate reject" buttons stand in for the real CI runner. In production, a runner claims the job and reports back automatically.
  • Money: prices are set and displayed; no real payments.
Why demo mode is safe
No credentials, no cloud services, no network access are required. The app bundles its own server (Node runs inside the Electron binary) and its own browser runtime. You can use it anywhere, including fully offline.

2 · Installation & first launch

2.1 Install from the installer

  1. Double-click Forge Pro-Setup-0.1.0.exe.
  2. If Windows shows a SmartScreen warning ("Windows protected your PC"), click More info → Run anyway. This happens because the installer is not code-signed yet — it is a normal caution for self-built apps. (See §10 for details.)
  3. Choose an install folder (the default under Program Files is fine) and finish the wizard.
  4. Launch Forge Pro from the Start menu or the desktop shortcut.
Prefer running from the source?
If you develop the Forge Pro repo, pnpm desktop:dev stages the runtime and launches the shell without installing anything. pnpm desktop:package rebuilds the installer.

2.2 First launch

On launch, the app starts its bundled server, waits until the portal answers, and opens the Vendor Dashboard. A banner reminds you that data is simulated. The portal lives at http://127.0.0.1:4310/vendor — you can also open that address in a normal browser.

2.3 Where your data lives

Demo store%APPDATA%\Forge Pro\demo-store\
App settings%APPDATA%\Forge Pro\

Everything you create (drafts, submissions, admin actions) is saved there and survives restarts. Deleting the demo-store folder resets the app to its factory demo data — see §10.

One window, two hats
The admin views are part of the same demo store, so actions you take as admin (approving a vendor, unpublishing an item) are immediately visible on the vendor dashboard — a handy way to see how the two sides of the marketplace interact.

4 · Step-by-step: submit your first template

We'll ship a landing-page template called "Aurora Landing Page" — the exact scenario a real vendor runs every day.

Deploy preview→ Catalog details→ Prove ownership→ Upload zip→ QA→ Report→ Publish & sell

Step 0 — Deploy a preview

Before you submit, deploy the template somewhere reachable — your own host, a static host, or localhost during development. The QA gate tests this URL, so it must be the real, working site.

Step 1 — Catalog details

  1. On the dashboard, click New submission.
  2. Item type — choose Template (choose Component for UI components; a Component type field then appears).
  3. Title — at least 3 characters, e.g. Aurora Landing Page.
  4. Description — at least 40 characters. Describe what it is, who it's for, what makes it good.
  5. Framework — Astro, Next.js, React, … (a suggestion list helps).
  6. Category — landing-page, dashboard, forms, …
  7. Stack tags — add up to 8, e.g. Tailwind, TypeScript (type, then Enter or comma).
  8. Price — between $0.01 and $500, with currency (USD / EUR / GBP / BRL). Example: 129 USD.
  9. Screenshots — optional, up to 6 images (5 MB each).
  10. Click Continue — preview & ownership.
Validation is immediate
Each field is validated as you go (zod rules): title length, description minimum, price range, and — for components — a required component type. Fix the highlighted field to continue.

Step 2 — Preview & ownership

Because the QA gate spends real CI minutes on your preview URL, Forge Pro requires proof you control it.

  1. Enter your deployed preview URL. It must be https (or localhost/127.0.0.1 during development).
  2. The form shows a verification token and ready-made meta tag. Copy the tag and paste it into the <head> of your preview page, then deploy: 
    <meta name="forge-pro:verify" content="<your-token>" />
  3. Click Verify ownership. The app fetches your page and confirms the token is present → verified.
  4. Click Continue — artifact & version.
Local previews work
Run the site on http://localhost:3000 while you build, add the token, and verify — no hosting needed to try the full loop.

Step 3 — Artifact & version

  1. Template source (zip) — choose your .zip. Constraints: real zip (PK magic bytes), max 50 MB. The app hashes it with SHA-256 and shows the size + hash preview.
  2. Version — semantic version, e.g. 1.0.0.
  3. Review — check the summary (type, title, framework, stack, category, price, preview URL, version, ownership status).
  4. Click Submit for QA.

You land on the submission page. The status chip moves to submitted with a queued/running job — just like a real submission waiting for the runner. In demo mode the page shows the Simulate pass / Simulate reject controls that stand in for the runner.

5 · Reading a QA report

Open a submission and click into its report. This is the exact report contract the live runner produces — the same score bars, the same thresholds, the same layout your customers will see attached to a live listing.

5.1 The verdict

One of three outcomes:

  • passed — every gate held. Eligible to go live with the QA Verified badge.
  • rejected — at least one suite failed. The report tells you exactly what and where.
  • error — the run itself failed (infra, not quality). Retryable; never a verdict on your item.

5.2 The score bars

Four Lighthouse categories, each with a minimum threshold and a weighted composite (the number in the dashboard's score column):

CategoryDefault minimumWeightWhat it measures
Performance5530%Load speed, LCP, CLS, TBT
SEO8520%Crawlability, meta, mobile-friendliness
Accessibility8535%Contrast, labels, keyboard, ARIA
Best Practices8015%HTTPS, console errors, modern APIs

A pass requires every category at or above its minimum and the composite at or above 75. One weak category can sink the composite even when the others are strong — the report shows the math.

5.3 The four suites

  • Smoke & responsive — the page loads at each breakpoint (320 → 1920 px) with no horizontal overflow, required elements visible, and zero error-level console messages.
  • Links — a crawl of the preview site; every internal link must resolve (no 4xx/5xx).
  • Visual — pixel diff against the previous baseline; must stay within the tolerance, or this run becomes the new baseline.
  • Lighthouse — the scores above.

5.4 Failed checks & the AI narrative

A rejected report lists every failed check with a precise detail — e.g. "scrollWidth 496px exceeds viewport width 320px" or "No visible element matching 'footer'". Rejected reports also include an AI narrative: a plain-language summary plus triaged issues, each with a suggested fix. It explains, it never decides — the verdict is the math.

Read the report like a reviewer
Start with the composite and the suite that failed, then open the failed-check details. Every check carries enough context to reproduce the problem in your own browser — which is exactly how you fix it (next section).

6 · Fixing a rejection and resubmitting

Rejections are the gate working as intended — and they're routine. Here is the loop, using the dashboard kit "Nimbus Dashboard Kit" from the demo data as the example.

6.1 What the rejection says

The demo kit's report shows: horizontal overflow at 320px (a grid with a fixed min-width), a footer hidden by a media query at tablet width, a client-side error (products.map is not defined), 2 broken links, and accessibility below 85. Each item maps to a concrete fix:

  • minmax(0, 1fr) grid columns (or overflow-x: clip) — kills the 320px overflow.
  • Check the footer's breakpoint media query — it targets 1024px while the layout switches at 1280px.
  • Guard the render while data loads (default to []).
  • Fix the 404 links; add labels/contrast for accessibility.

6.2 Resubmit

  1. Fix the code in your project, rebuild the zip, bump the version to 1.1.0.
  2. From the rejected submission page, start a resubmission (the same three-step flow).
  3. The gate runs again against the new artifact — the report and badge always describe the artifact hash they tested.
  4. Pass → the listing moves toward published with the new report attached.
Why versions matter
Each submission records submittedVersion and the artifact's SHA-256. A verdict is only meaningful for the exact artifact tested — resubmitting with a bumped version keeps the audit trail honest.

7 · Withdrawing a submission

You can withdraw a draft, a submitted item still in the queue, or a rejected item you'd rather shelve than fix. Withdrawn items keep their history but leave the marketplace flow.

You can't withdraw a published listing from the vendor side
Once live, unpublishing is an admin action (see §8) — that separation is deliberate: vendors manage submissions, admins govern the catalog.

8 · Admin: approve vendors & unpublish items

Switch hats and visit the admin area — the marketplace operator's side of the window.

8.1 Vendor applications (/admin/vendors)

New vendors apply with a bio, website, and role. Review the application and click:

  • Approve — the application flips to approved and the user's role becomes vendor.
  • Revoke — removes vendor status (role back to buyer); the same control doubles as the "fire the vendor" lever.

The demo data ships with two pending applications (Maya Chen, Jon Rivers) and one approved vendor (Diego Souza) so you can approve, revoke, and re-approve freely.

8.2 All submissions (/admin/submissions)

Every submission in the marketplace, with vendor names and statuses. Click Unpublish on any live item to take it down. The item immediately shows the unpublished tag on the vendor dashboard and disappears from the live catalog.

Governance, end to end
Approve a vendor → that vendor's submissions appear in your admin list → unpublish one and watch the tag ripple through both dashboards. The demo is a working model of the marketplace's trust layer.

9 · Example journeys — from deployment to sale

Case A · Ship a landing-page template (the happy path)
  1. You build "Aurora Landing Page" and deploy a preview with the verification meta tag.
  2. New submission → Template → fill catalog details → verify ownership → upload the zip → Submit for QA.
  3. Simulate the runner → Simulate pass.
  4. Open the report: composite 84.2, all four suites green, 0 failed checks.
  5. The listing is published with the QA Verified badge and its score attached — buyers see a machine-tested item, not a promise.
  6. Sale: the price you set ($129) is what the marketplace charges; licenses and checkout are the live system's job. In the demo, the money step is represented by the price on the listing.
Case B · Fix a rejected dashboard kit (the iteration loop)
  1. "Nimbus Dashboard Kit" comes back rejected — overflow at 320px, a hidden footer, a runtime error, 2 broken links, accessibility 64.
  2. The AI narrative groups the issues with suggested fixes; the failed-check list pinpoints each line.
  3. You fix the grid, guard the render, repair the links, bump to 0.9.2, resubmit.
  4. This time it passes — the report now shows the new artifact's hash and score. Rejection isn't a dead end; it's the gate teaching your code to pass.
Case C · Run the marketplace as an operator
  1. A new vendor applies → you approve them in /admin/vendors; their submissions appear in your admin list.
  2. One of their items goes live, then a support report flags it → Unpublish from /admin/submissions.
  3. The vendor dashboard instantly shows the unpublished tag; the item is out of the catalog.
  4. If trust breaks down, Revoke removes the vendor role entirely.
Case D · Withdraw a listing you no longer want to ship
  1. You submitted a form kit, but the scope changed mid-QA. From the submission page, Withdraw.
  2. The status becomes withdrawn; the row stays in your history with its (partial) report.
  3. Start fresh whenever you're ready — drafts and submissions are cheap; the gate is the expensive part, and you only pay it on purpose.

10 · Tips, reset & troubleshooting

Reset to the factory demo

  1. Close Forge Pro.
  2. Delete the folder %APPDATA%\Forge Pro\demo-store.
  3. Relaunch — the app reseeds its original demo data on first load.

Common issues

SymptomCause / fix
SmartScreen warning on installInstaller is not code-signed. Click More info → Run anyway. A signed build removes this (see below).
"The portal runtime is missing" dialogThe bundled runtime wasn't staged. In a dev checkout, run pnpm desktop:prepare then relaunch.
"Could not start the portal" / port busyAnother instance or app holds port 4310. Set FORGE_PORT to a free port before launching (the app reads it from the environment).
Second launch opens but no new windowSingle-instance lock: the first window is focused instead — by design.
Dashboard looks emptyThe demo store was reset or is from an old format; relaunch once or delete demo-store to reseed.
Simulate buttons missingSimulation only appears for submitted items with a queued job — and only in demo mode.

Good habits

  • Verify before you submit. The ownership proof exists because QA runs cost real resources; a failing verification means the gate would test the wrong thing.
  • Keep preview URLs stable. The report is bound to the URL and artifact hash tested. Redeploying after a pass invalidates nothing, but re-running QA against a changed preview is the honest move.
  • Bump versions on every resubmission. It keeps the audit trail and the badge honest.
  • Use the admin views as your quality review. Approve slowly, unpublish fast — that's the trust loop the whole product is built on.
Making the installer production-ready
For distribution beyond your own machine: add an application icon (electron-builder win.icon), sign the installer with a code-signing certificate to remove the SmartScreen warning, and rebuild with pnpm desktop:package. The build is fully reproducible from the Forge Pro repo.
